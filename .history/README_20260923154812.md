# University Student Record and Campus Route Management System

A complete Java console application for a Data Structures and Algorithms assignment. It manages student records and service requests, records recent actions, and models campus locations and roads. All lists, queues, stacks, hash chains, trees, graph adjacency lists, and traversal structures are implemented manually. No Java Collection Framework classes, external libraries, or build dependencies are used.

## Objectives

- Apply encapsulation, inheritance, composition, and clear separation of responsibilities.
- Demonstrate how different data structures support university administration.
- Keep student records consistent across a singly linked list, hash table, and AVL tree.
- Implement searching, sorting, BFS, and DFS with understandable Java code.
- Provide a reliable interactive demonstration with input validation and automated tests.

## Data model and validation

Each `Student` holds **Student ID, name, age, gender, degree programme, email, contact number, address, and GPA**. Records are immutable. Updating creates a fully validated replacement before changing the indexes, so incomplete input cannot leave a partial update.

- IDs are trimmed and normalized to uppercase. They contain 1–40 letters, digits, hyphens, or underscores, beginning with a letter or digit. IDs are unique irrespective of case.
- Required fields cannot be blank. Age is an integer from 1 to 120. Gender and programme are free text.
- GPA must be finite and within 0.00–4.00 inclusive. `NaN` and infinity are rejected.
- Email validation checks a basic `name@domain.suffix` form. It does not verify deliverability.
- Phone numbers contain 7–15 digits, with optional spaces, parentheses, hyphens, and an initial `+`.
- Menus reject invalid numbers and text and prompt again. Missing records and empty structures have clear messages.
- Requests must reference an existing student. A student with pending requests cannot be deleted until those requests have been processed, preventing orphan requests.
- Location names are trimmed and compared without case sensitivity. Roads require two different existing locations and a positive finite distance.
- Duplicate roads are rejected in either direction. To change a distance, remove and re-add the road.
- Closing input exits gracefully. Incomplete student creation or editing does not modify stored records.

**Data is stored in memory for the current process only.** There is no database or file persistence. A normal launch starts empty. `--demo` loads the fictional sample below. All distances use metres; demo roads do not represent a real campus map.

## Data structures and algorithms

### Singly linked list

`StudentLinkedList` owns `StudentNode` links, a head, a tail, and a size counter. It appends records in insertion order, searches by ID, replaces records without changing their position, deletes head/middle/tail nodes, and traverses into an array for display or algorithms. Arrays returned to callers are independent snapshots; immutable student objects can safely be shared.

### Queue

`ServiceQueue` uses `QueueNode` links with front and rear references. Enqueue adds at the rear; dequeue removes the front, enforcing FIFO. Requests contain a request ID, student ID, type, and description. The system generates `REQ-1`, `REQ-2`, and so on during each session.

### Stack

`ActionStack` uses `StackNode` links with a top reference. Push, pop, and peek follow LIFO. Timestamped `Action` entries cover student additions, updates, deletions, searches, service operations, graph changes, and traversals. Display runs from newest to oldest.

### Hash table

`StudentHashTable` implements a polynomial hash manually:

```text
hash = 0
for each character in normalized ID:
    hash = (31 * hash + character) mod capacity
```

Long intermediate arithmetic prevents multiplication overflow at normal array capacities. Collisions use custom linked `Entry` chains. The initial capacity is 17; crossing 0.75 load grows capacity to `2 * capacity + 1` and rehashes entries. Insert rejects duplicate IDs, and update replaces only an existing entry. The bucket display makes collision chains visible.

### BST and AVL tree

`StudentBST` provides insertion, search, update, deletion, and inorder traversal using `TreeNode`. Two-child deletion replaces the node with its inorder successor. `AVLTree` extends the BST and restores balance with LL, RR, LR, and RL rotations after insertion and deletion. The running application uses **AVLTree**; both classes are implemented and tested.

Tree keys are **student IDs**, ordered lexicographically. For example, `S10` sorts before `S2`; zero-padded IDs such as `23DA2-0001` preserve the expected numeric suffix order. GPA rankings are produced separately by merge sort. Equal GPA values share competition ranks, such as `1, 1, 3`, with student ID used to order tied entries deterministically.

### Graph

`CampusRouteGraph` is an undirected weighted graph. Vertices live in a manually resized `Location[]`; each location owns a linked adjacency list of `Edge` objects. A bidirectional road is stored as two edges. Vertex removal unlinks incoming edges and compacts the vertex array while preserving the remaining references.

- **BFS:** a manually managed integer array queue explores the starting location level by level.
- **DFS:** a manually managed array stack of adjacency cursors explores a branch before backtracking. It avoids recursive call-stack limits.
- Visited arrays prevent revisits in cycles. Neighbor order follows road insertion order, giving deterministic output.
- Traversals visit only the connected component of the selected start; output reports how many of all campus locations were reached. Isolated vertices remain visible in the campus display.
- Distances are stored and displayed. BFS/DFS demonstrate reachability and traversal; weighted shortest-path calculation is outside this assignment's specified algorithms.

### Searching and sorting

`SearchAlgorithms` provides linear and binary search by ID and name. Name matching is exact and case insensitive, and **all** matching names are returned. Binary search sorts a copy on the appropriate key before searching, so it works even when the linked list is unsorted.

`SortingAlgorithms` implements stable merge sort manually for ID ascending, name ascending, and GPA descending. Name and GPA ties use ID ascending. Sorting never changes linked list insertion order. No `Arrays.sort`, `Collections`, collection implementations, streams, or graph libraries are used.

### Complexity

Let `n` be the number of students, `q` the number of waiting requests, `h` the history size, `V` locations, and `E` undirected roads.

| Operation | Time | Notes |
| --- | --- | --- |
| Linked list search/update/delete | O(n) | Sequential link traversal. |
| Linked list add | O(n) | Duplicate check; linking at the tail itself is O(1). |
| Queue enqueue/dequeue/peek | O(1) | Queue display and pending-student check are O(q). |
| Stack push/pop/peek | O(1) | Display is O(h). |
| Hash search/insert/delete | Expected O(1), worst O(n) | Resizing is O(n); insertion is expected amortized O(1). Assumes bounded ID length. |
| BST search/insert/delete | O(tree height), worst O(n) | Unbalanced comparison implementation. |
| AVL search/insert/delete | O(log n) | Inorder traversal is O(n). |
| Linear search | O(n) | Name results may include multiple matches. |
| Binary search phase | O(log n), or O(log n + matches) by name | Sorting the copy first makes each public search O(n log n) overall. |
| Merge sort | O(n log n) | O(n) auxiliary space. |
| Graph find/add location | O(V) | Linear name lookup; vertex array growth is amortized. |
| Graph add/remove road | O(V + degree) | Includes endpoint name lookup and adjacency search. |
| Graph remove location/display | O(V + E) | Removes all incident roads or displays all adjacency lists. |
| BFS/DFS | O(V + E) | O(V) working memory; counts refer to all vertices and reachable edges. |

An application-level student add/update/delete still includes the O(n) linked list operation. Deletion also checks pending requests in O(q). Hash and AVL indexes provide fast independent lookups and sorted traversal; they do not remove the list's mutation cost.

## Technologies and OOP design

- Java 17 language target and standard JDK only.
- VS Code launch settings and PowerShell/POSIX shell build scripts.
- Git/GitHub collaboration files and a Java 17 CI workflow.
- Private fields encapsulate records and data structure ownership.
- Immutable value objects represent students, requests, and actions.
- `AVLTree` inherits the base BST operations and overrides the balancing hook.
- `UniversitySystem` composes the structures and coordinates mutations; `ConsoleApplication` handles presentation; `ConsoleInput` handles validated input.

`java.util.Locale` is used only for deterministic text casing and numeric formatting; it is not a collection. Other standard-library types support I/O and timestamps. All data structure storage and algorithms are custom.

## Testing details

The dependency-free runner performs 12 suites and **53,400 assertions**. It covers record validation; list boundaries; queue FIFO and stack LIFO; deliberate hash collisions and growth; BST deletion; all four AVL rotations and randomized mutation; duplicate-name searching and sort order; cyclic/disconnected graph traversal and vertex deletion; synchronized indexes; and all 16 console options.

It also checks malformed numeric input, missing records, empty structures, `NaN`/infinity, and interruption during student creation and editing. The fixed random seed makes model-based checks reproducible. Assertions throw on failure without requiring Java's `-ea` flag.

Local verification used JDK **23.0.2** with `--release 17`, with no compiler warnings. The included GitHub workflow is configured to run tests on an actual Java 17 runtime after the project is pushed. See [testing details](docs/TESTING.md) for scenarios and test output.
